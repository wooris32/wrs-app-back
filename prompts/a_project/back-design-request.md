# WR Backend 프로젝트 설계 요청서

## 1. 프로젝트 개요

* **프로젝트명:** WR
* **Backend Git 저장소:** `wrs-app-backend`
* **Frontend Git 저장소:** `wrs-app-frontend`
* **Backend 개발 환경:** Java 및 Spring Boot 기반 REST API 서버
* **Git 관리 원칙:** Frontend와 Backend는 독립된 Git 저장소로 관리
* **Java 패키지 기준:** `com.wrs.app`
* **Spring Boot Application 명칭:** `WrsAppBackendApplication`

---

## 2. 기술 스택

다음 기술을 기준으로 설계한다.

* **Java 21**
* **Spring Boot 3.5.x**
* **Gradle**
* **Spring Data JPA**
* **Hibernate**
* **PostgreSQL**
* **Redis**
* **REST API**

### 기술 선택 및 적용 원칙
* ORM은 JPA를 기본으로 사용한다.
* 일반적인 조회, 생성, 수정, 삭제는 Spring Data JPA를 사용한다.
* 복잡한 조회나 통계 쿼리는 QueryDSL 또는 Native SQL 도입 여부를 검토한다.
* 처음부터 불필요하게 여러 데이터 접근 기술을 혼합하지 않는다.
* MyBatis 및 XML Mapper 구조는 기본 설계에 포함하지 않는다.
* 기술 버전과 상호 호환성은 공식 문서를 기준으로 확인한다.

## 3. 기본 디렉터리 구조

다음 구조를 기본안으로 검토하되, 도메인 규모에 맞게 조정한다.

```text
wrs-app-backend/
├── src/
│   ├── main/
│   │   ├── java/
│   │   │   └── com/wrs/app/
│   │   │       ├── config/
│   │   │       ├── controller/
│   │   │       ├── service/
│   │   │       ├── repository/
│   │   │       ├── domain/
│   │   │       ├── dto/
│   │   │       ├── exception/
│   │   │       └── common/
│   │   └── resources/
│   │       ├── application.yml
│   │       ├── application-local.yml
```

### 아키텍처 원칙
* JPA 기반 구조이므로 Entity, Repository, Service, Controller의 책임을 명확히 분리한다.
* DTO와 Entity를 직접 혼용하지 않는다. 패키지 구조는 단순 계층형과 도메인별 구조를 비교한 뒤 유지보수에 적합한 방식으로 제안한다.

## 4. Database 설계

PostgreSQL을 기본 데이터베이스로 사용한다.

### 주요 설계 항목
* 기본키 및 식별자 전략
* 테이블 간 관계
* 인덱스
* 유니크 제약조건
* NOT NULL 및 CHECK 제약조건
* 생성일 및 수정일
* 논리 삭제 필요 여부
* 낙관적 락 및 동시성 제어
* 날짜·시간 및 타임존 저장 기준

### 운영 및 마이그레이션 원칙
* 운영 환경에서는 Hibernate의 자동 테이블 생성 및 변경에 의존하지 않는다.
* DB 스키마 변경 이력을 관리하기 위해 Flyway 도입을 검토한다.
* 초기 데이터 및 관리성 데이터는 SQL을 통해 직접 입력할 수 있도록 한다.
* 관리자 Back-office가 없는 현재 단계에서는 DB 클라이언트 또는 SQL 스크립트를 통한 데이터 등록을 전제로 한다.
* 단, 서비스의 일반적인 일정 생성·수정·삭제는 Frontend가 REST API를 통해 처리한다.

---

## 5. 핵심 도메인: 일정 관리

WR의 가장 중요한 기능은 사람별 일정 관리다.
Frontend 스케줄러는 React Big Schedule을 우선 적용 대상으로 한다. 일정 데이터는 Backend에서 관리하고 PostgreSQL에 저장한다.

### 지원 업무 기능
1. 일정 목록 조회
2. 일정 상세 조회
3. 일정 생성
4. 일정 수정
5. 일정 삭제
6. 담당자 변경
7. 일정 시작 시간 변경
8. 일정 종료 시간 변경
9. 일정 복사
10. 일정 중복 및 충돌 검증

### 일정 데이터 기본 필드 후보
* 일정 ID
* 일정 제목
* 일정 설명
* 담당자 ID
* 시작 일시
* 종료 일시
* 일정 상태
* 일정 유형
* 생성일
* 수정일
* 버전 (동시성 제어가 필요한 경우)

### 주요 정책
* 사람 정보와 일정 정보는 분리한다. 실제 업무 요건을 검토해 필드를 확정하고, 필수값·선택값·제약조건을 명시한다.
* 일정 복사는 원본 일정을 그대로 덮어쓰는 방식이 아니라 신규 일정 생성으로 처리하는 방향을 검토한다. 복사 시 제목, 담당자, 시간, 기타 속성을 어떻게 초기화할지 정책을 제안한다.

## 6. 일정 충돌 및 동시성 처리

여러 사용자가 동시에 일정을 조회하거나 수정할 수 있으므로 충돌 처리가 필요하다.

### 설계 항목
* 동일 담당자의 일정 중복 허용 여부
* 일정 중복 검증 로직
* 일정 이동 시 충돌 검증
* 일정 시간 변경 시 충돌 검증
* 동시에 동일 일정을 수정하는 경우의 처리
* 트랜잭션 범위
* 낙관적 락(`@Version` 등) 적용 여부
* DB 제약조건으로 보장할 수 있는 범위

### 핵심 원칙
* 동일 담당자의 일정 중복을 기본적으로 방지하는 방향을 제안하되, 실제 업무 규칙에 따라 확정한다.
* 시간 구간의 시작·종료 경계 처리(예: 종료 시각과 다음 일정 시작 시각이 같은 경우)를 명확히 정의한다.
* Frontend에서 충돌 여부를 먼저 확인하더라도 Backend에서 최종 검증한다.

---

## 7. REST API 설계

Frontend와 공유할 API 명세를 별도로 관리한다.

### 주요 API 분류
* **사용자 및 담당자:** 사용자 정보 조회, 담당자 목록 조회, 담당자 상세 조회
* **일정:** 기간별 일정 목록 조회, 일정 상세 조회, 일정 생성, 일정 수정, 일정 삭제, 일정 이동, 일정 복사, 일정 충돌 검증

### API 설계 원칙
* 일정 조회는 시작일과 종료일을 기준으로 한다. 전체 일정을 무조건 조회하지 않도록 기간 조건 및 필요한 필터를 설계한다.
* 각 API에 대해 URL, HTTP Method, Path 및 Query Parameter, Request DTO, Response DTO, HTTP Status, 오류 응답 규격, 인증 및 권한 조건을 문서화한다.
* Frontend와 API 계약을 공유할 수 있도록 OpenAPI/Swagger 도입을 검토한다.

---

## 8. 인증 및 권한

웹 및 모바일에서 동일한 Backend API를 사용할 수 있도록 인증 구조를 설계한다.

### 검토 항목
* 로그인 방식
* Access Token 및 Refresh Token
* 사용자 권한
* 인증 실패 처리
* API 접근 권한
* 비밀번호 암호화
* CORS
* 토큰 만료 및 재발급 정책

### 설계 방향
* 구체적인 인증 정책은 아직 확정하지 않았으므로 적절한 선택지와 장단점을 설계안에 제시한다.
* 현재 Back-office가 없더라도 향후 관리자 기능을 추가할 수 있도록 권한 모델의 확장성을 고려한다. 단, 현재 범위에 불필요한 관리자 기능을 구현하지 않는다.

---

## 9. Redis

Redis는 초기 기술 스택 후보에 포함되어 있다. 실제 필요성을 검토하고 다음 용도를 평가한다.

* 세션 또는 토큰 관리
* 캐시
* 임시 데이터
* 중복 요청 방지

필요하지 않은 기능에 Redis를 무조건 적용하지 않는다. 도입하지 않는 경우에도 향후 추가하기 쉬운 구조인지 검토한다.

---

## 10. 환경 설정 및 보안

* **기본 프로파일:** `local`, `prod`
* **보안 원칙:**
  * 환경별 DB 접속 정보 및 민감정보는 외부 설정으로 분리한다.
  * 비밀번호, Secret, 토큰, 운영 DB 접속 정보 등을 Git에 커밋하지 않는다.
  * 로그에 비밀번호, 토큰 및 민감한 사용자 정보를 남기지 않도록 설계한다.

---

## 11. Back-office 및 초기 데이터 관리 방침

* 관리자용 Back-office는 현재 개발하지 않으며, 향후 별도 Frontend 프로젝트로 개발할 예정이다.
* **현재 운영 방침:**
  * 초기 데이터는 DB에 직접 입력한다.
  * 관리성 데이터는 SQL 스크립트로 입력한다.
  * DB 스키마 변경은 마이그레이션 파일로 버전 관리한다.
  * 일반 서비스 기능은 REST API를 통해 처리한다.
  * 현재 Backend에 관리자 화면 전용 API를 불필요하게 추가하지 않는다.
* 향후 Back-office가 추가되더라도 기존 도메인 모델과 서비스 로직을 재사용할 수 있도록 설계한다.

---

## 12. Git 관리

* `wrs-app-backend`는 독립적인 Git 저장소다.
* Frontend 저장소와 Git 이력을 공유하지 않는다.
* 최상위 작업 폴더 `WR`은 Git 저장소로 만들지 않는다.
* Backend 저장소 내부에서만 Git 관리가 이루어지도록 설계한다.
